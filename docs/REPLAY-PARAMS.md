# 历史版本参数回填与重跑

> 一句话：点历史版本 → 把那条任务的输入原样填回表单 → 改完重新生成一条**新**任务，原任务不动。

---

## 1. 回填哪些参数

任务记录里有三类信息，只有第一类属于「输入」，才回填：

| 来源字段 | 是否回填 | 说明 |
|---|---|---|
| `jobs.input`（工具表单全部字段） | **是** | 文字、下拉、多选、滑块、上传都算 |
| `jobs.model_key` | **是** | 当初选定的模型；为空表示「自动路由」，回填后仍保持自动 |
| `jobs.prompt_version` | 否 | 只做审计，不是用户输入 |
| `jobs.output` / 关联素材 | 否 | 属于原任务的产出，新任务重新生成 |
| `jobs.cost_cny` | 否 | 历史成本快照；新任务按**当前**单价与参数重算 |
| `jobs.status` / `error_*` | 否 | 新任务一律从 `queued` 开始 |

### 逐字段类型的转换规则

| 字段类型 | 规则 | 为什么要这样 |
|---|---|---|
| `text` / `textarea` | 原样带入，不 trim | 用户可能刻意保留换行与空格 |
| `select` | 值在当前 `opts` 里才用，否则回落默认 | `<select>` 的 value 不在选项里时会**显示第一项、但内部值仍是旧的**，看着对、提交是错的 |
| `picks`（单选/多选） | 逐个过滤失效选项；全失效则回落默认 | 同上，且多选是逗号串，要重组 |
| `range` | `clamp(min, max)` | 工具改过上下限时，滑块位置与实际值必须一致 |
| `upload` | 原样带回素材 id 串（逗号分隔） | 提交时 pipeline 认的就是 id；同时按 id 拉一次素材详情用于显示文件名 |
| 已从 schema 删除的字段 | **丢弃** | 不能把废弃字段塞进新任务的 input |

被丢弃或重置的字段会汇总成一句提示，例如：
> 已载入 10-20 18:02 的参数：语气（选项已变更）在当前版本已不可用，已回落默认值

## 2. 回填时机与触发条件

**触发条件**：点击「历史版本」列表里的任意条目（不限状态）。

**时机**：点击后立即执行，与切换产出预览是同一次交互：

1. 同步切 `jobId` → 右侧立即显示该任务的产出（不等回填完成）
2. 解析 `input` → `mergeInput()` 清洗
3. 异步按 id 拉上传素材（最多 6 个并发单查）
4. 通过 `key` 重建表单组件，一次性把清洗后的值灌进去

**为什么用 key 重建而不是 `useEffect` 同步**：受控表单在挂载后再 `setValues` 会出现一帧旧值、以及光标/滚动位置跳动；重建组件是最干净的重置方式，代价只是丢焦点——而这一步本来就是用户主动发起的导航。

### 幂等与草稿保护

| 情况 | 行为 |
|---|---|
| 已载入该版本，且用户没改过 | **不重复回填**（避免打乱光标与滚动位置），只切预览 |
| 表单有未提交的改动 | 弹确认框「当前配置有未提交的修改，载入这条历史版本会覆盖它」，取消则**连预览也不切** |
| 该任务 `input` 为空 | 不回填，提示「这条任务没有保存输入参数，只能查看产出」 |
| 点了「恢复默认」 | 清空回填来源、表单回到工具默认值，下次提交不再挂 parent |

## 3. 重新入队后与原任务的关系

提交 = 新建一条任务，**不是**修改或重跑原任务。

| 维度 | 新任务 | 原任务 |
|---|---|---|
| `id` | 新生成 | 不变 |
| `parent_job_id` | 指向参数来源任务 | 不变 |
| `input` | 用户确认后的参数 | 不变 |
| `status` | 从 `queued` 开始 | **不变**（哪怕它是 failed / canceled） |
| 产出与素材 | 自己的 | 自己的，不被覆盖也不转移 |
| 积分 | 按新参数重新报价并扣一次 | 已有的扣费/退款记录不动 |
| 审计 | `job.created` 带 `parentJobId` | 不动 |

### parent 链的语义

`parent_job_id` 记的是「**这次的参数是从哪条改出来的**」，于是：

- 从 A 载入 → 提交得到 B：`B.parent = A`
- 在 B 的基础上接着改 → 提交得到 C：`C.parent = B`（形成可追溯的修改链）
- 再从 A 载入一次 → 提交得到 D：`D.parent = A`（与 B 是平行派生，不是覆盖）

服务端会校验：parent 必须属于同一 org、且 `tool_slug` 一致，否则分别返回 `PARENT_NOT_FOUND` / `PARENT_MISMATCH`。生产上这两个 404/422 也顺带挡住了「拿别人的 job id 串进来」的越权尝试。

## 4. 边界情况与预期行为

| # | 场景 | 预期行为 |
|---|---|---|
| 1 | 原任务 `succeeded` | 正常回填；主场景 |
| 2 | 原任务 `failed` | **同样回填**——这是最有价值的场景：改一个参数直接重试，比重新填一遍省事 |
| 3 | 原任务 `canceled` | 同上 |
| 4 | 原任务还在跑（`queued`/`running`/…） | 允许回填与提交，两条任务并行；不阻塞、不合并 |
| 5 | 上传的原文件已被删除 | 该字段置空并提示「原上传文件已失效（参考图），请重新上传」，**不带着死 id 提交** |
| 6 | 工具改版：选项被删 | 该字段回落默认值，提示里点名是哪个字段 |
| 7 | 工具改版：新增字段 | 用该字段默认值，不提示（属正常升级） |
| 8 | 工具改版：滑块上下限变了 | 值 clamp 到边界，不报错 |
| 9 | 当前积分不足以支付新任务 | 提交返回 402，**新任务不创建**；表单内容保留，不做任何写入 |
| 10 | 新任务生成失败 | 失败退回逻辑与原任务独立，只退新任务那一单 |
| 11 | 连点「生成」 | 提交期间按钮 disabled（`create.isPending`），不会重复建单 |
| 12 | 载入的模型当前不可用（Key 失效/套餐降级） | 回填仍保留该选择；提交时后端返回 `MODEL_UNAVAILABLE` 并说明原因，用户改选其他模型即可 |
| 13 | 载入的模型已从目录移除 | 下拉里找不到该 key，回落「自动」，提示同 #6 |
| 14 | 历史列表只显示最近 8 条 | 回填不依赖列表项是否还在视口内；`seedFrom` 与时间单独存状态 |
| 15 | 原任务被清理脚本删除 | 提交时 parent 校验失败（`PARENT_NOT_FOUND`），前端把提示转成「来源任务已不存在，本次将作为新任务提交」并清空 parent |

| `src/lib/domain/tools.ts` | 新增 `mergeInput()`：清洗历史 input（丢废弃字段、过滤失效选项、clamp 滑块、返回 `dropped` 清单） |

## 6. 明确没做的部分

列出来免得被当成 bug：

- **不做参数 diff**：不显示「这一版比上一版改了哪几个字段」。需要的话是独立功能。
- **不做「覆盖原任务」**：历史记录只增不改，这是账本式设计的前提。
- **不自动重跑**：载入参数后仍需用户点一次「生成」，避免误扣积分。
- **不继承原任务的模型快照**：若目录里该 key 已下线，按「不可用」处理（#12/#13），不静默换模型。
- **不做 root 追溯**：只有 `parent_job_id` 单级指针，没有 `root_job_id`。要展示完整链路就沿 parent 递归，深度上限 32。
